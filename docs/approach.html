Reverse Engineering the LinkedIn Profile API

How an undocumented internal API was located, how its authentication and response format work, and how that becomes a clean hosted API of our own.

Author  Vishant Shah Date  27 August 2026 Deadline  31 August 2026 Status  Design complete, build in progress

01The challenge

Build a publicly hosted API that accepts a LinkedIn profile URL and returns the information on that profile as structured JSON, obtained by reverse engineering LinkedIn's own APIs. The response schema is ours to design.

The framing matters. This is not a request to scrape a web page — it explicitly asks for LinkedIn's APIs to be reverse engineered. Those two things produce very different systems, and the distinction shapes every decision below.

02How a LinkedIn profile page actually works

Loading linkedin.com/in/<slug> does not deliver a finished page. The browser receives a largely empty shell, and the JavaScript inside it then issues its own background requests to LinkedIn asking for the profile data. Those requests return clean, typed JSON, which the JavaScript paints into HTML.

The structured data therefore already exists upstream of anything visible. The requests go to paths beginning /voyager/api/ — Voyager being LinkedIn's internal name for the private API its own front end talks to. It is undocumented, unsupported, and not intended for outside use. Its existence is known only because its traffic is observable.

Two things are called "the LinkedIn API"

LinkedIn's official Developer API is fully documented, partner-gated and OAuth-authenticated — and it cannot return an arbitrary person's profile at all, only the authenticated user's own or those of people who explicitly authorise the calling application. It cannot satisfy this brief under any configuration.

Voyager is the internal surface. Discovering it, working out its authentication, and decoding its response grammar is the reverse engineering the challenge asks for.

03Discovery method

No documentation exists, so the endpoints were found by observation: open a profile in a logged-in browser, open the network inspector, filter for /voyager/, and read what the page requests of its own accord.

One page load produced six such calls. Most are noise — presence polling, notification badge counts, telemetry beacons. One carries the profile. Separating signal from noise is most of the discovery work; the request itself is a single line.

04What was verified

The following call was executed against a real logged-in session and returned HTTP 200 with 12,417 bytes of JSON:

GET /voyager/api/identity/dash/profiles
      ?q=memberIdentity
      &memberIdentity=<publicIdentifier>
      &decorationId=com.linkedin.voyager.dash.deco.identity.profile.WebTopCardCore-6

csrf-token: ajax:<JSESSIONID value>
accept: application/vnd.linkedin.normalized+json+2.1
x-restli-protocol-version: 2.0.0
cookie: li_at=<session>; JSESSIONID=<...>

Each header buys exactly one behaviour, established by removing them individually:

HeaderRemovedWhat it does
cookie302 → /loginCarries the session. Without it you are anonymous.
csrf-token403Echo of the JSESSIONID value, proving the request came from a real LinkedIn page.
accept200, wrong shapeRequests the flattened representation. This single header creates the response format everything else depends on.
x-restli-…400Selects Rest.li 2.0 encoding for URNs and list parameters.

Two surfaces run in parallel

Alongside the REST endpoints above, LinkedIn now serves a GraphQL surface at /voyager/api/graphql. It uses persisted queries: the client may not send query text, only a name and a hash of a query the server already stores, as queryId=voyagerPremiumDashFeatureAccess.c87b20da…. Valid hashes cannot be invented — they must be harvested from observed traffic, and LinkedIn rotates them. Its parameters also use Rest.li's own URL encoding, variables=(a:b,c:List(x,y)), which is not JSON.

The REST surface is therefore the primary source and GraphQL the fallback: it avoids the rotating-hash problem entirely, and it is the one confirmed working.

05The response format is the real problem

Voyager speaks Rest.li, LinkedIn's own RPC framework, and its responses are not nested documents. They are a flat array of loose objects that reference one another by URN — LinkedIn's namespaced identifier format.

{
  "data": { "*elements": [ "urn:li:fsd_profile:ACoAADF3cUc…" ] },   // a pointer, not a person
  "included": [
    { "$type": "…identity.profile.Profile",
      "firstName": "…", "lastName": "…", "headline": "…",
      "*experienceCard": "urn:li:fsd_profileCard:(ACoAA…,EXPERIENCE)",   // an address
      "*educationCard":  "urn:li:fsd_profileCard:(ACoAA…,EDUCATION)" },
    { "$type": "…profile.Card", "entityUrn": "urn:li:fsd_profileCard:(…,EXPERIENCE)", … },
    // six more, all siblings
  ]
}

The governing rule: a field name beginning * holds an address, not a value. A person's jobs are not inside the person; they are a URN that must be resolved against included[].

Producing one clean profile therefore requires building a URN-to-object index, walking every pointer, and reassembling the graph into a nested document. That reconstruction — not the HTTP call — is the substantive engineering of this project. A further lever, decorationId, selects which slice of the graph the server returns at all; mapping useful decoration IDs to the sections the brief requires is the remaining discovery work.

06Choosing the transport

The obvious question is whether a headless browser is needed. It is not, and the reasoning is worth stating because it inverts the common assumption.

Headless browsers exist to execute JavaScript and build a page. Voyager returns JSON. There is no page to render, so on its only real strength a browser contributes nothing here. What it would contribute is request realism — and there is a far smaller tool for that.

Bot detection begins at the TLS handshake, before any header is parsed. The cipher suites a client offers, their order and the extension set form a recognisable pattern, hashed into a JA3 fingerprint. A default Python HTTP client produces a JA3 that identifies it as Python, and no amount of setting a browser User-Agent conceals that.

curl_cffi resolves this directly. It is a Python binding over a patched libcurl that reproduces a real browser's TLS and HTTP/2 handshake:

from curl_cffi import requests
r = requests.get(url, headers=HEADERS, impersonate="chrome")

A browser appears in this project exactly once, and never in production: a local one-off step to log in and capture the session cookie. Even that is optional, since the value can be copied from the browser's own developer tools by hand.

How this compares to the reference example

The brief cites PhantomBuster's LinkedIn Profile Scraper. Its own public API discloses its inputs: a profile URL, the user's li_at cookie, and the user's User-Agent string. Requiring the third is informative — a real browser supplies its own, so asking the user for it indicates requests are being constructed by hand and replayed server-side. Their product page also states the scraper does not return profile pictures, full work history, skills or endorsements, which are split into a separate product. This brief asks for all of them from one endpoint.

07API design

The schema being ours to design is an opportunity rather than a blank. Tross publishes documented operations across ten integrations, and they follow one rigid house style. Matching it deliberately demonstrates that their platform was read as carefully as LinkedIn's.

Conventions adopted from Tross's own documentation

POST for every operation, reads includedfetch-patient-info, fetch-claims, fetch-appointments are all POST
/api/integrations/{vendor}/{verb-noun}kebab-case, verb first, no version segment anywhere

Their auth_id is the most instructive detail: credentials for each upstream portal are stored server-side and referenced by opaque handle, never passed per request. Adopting it satisfies the brief's requirement to keep secrets out of the repository as a structural property rather than a convention.

On auth_id, and why credential provisioning stays off the API

Every Tross operation requires an auth_id documented only as "Auth id". Their documentation carries no authentication page, no getting-started guide, and — decisively — no endpoint anywhere that accepts a credential. Provisioning happens entirely outside the documented API; their marketing site directs prospects to book a demo.

That is a security property rather than an omission: an API with no endpoint that accepts credentials has no endpoint that can leak them or be abused to harvest them. This API takes the same posture. auth_id is an opaque handle resolved server-side, and no route accepts a LinkedIn credential.

Here it resolves to a single operator-held session supplied through the environment, which is precisely what the brief specifies — "You may use your own LinkedIn credentials in the backend." Multi-credential support would be a storage change behind the same interface, plus auth_id added to the cache key, since LinkedIn discloses different amounts of a profile depending on the viewing account and a shared cache would otherwise serve one session's data to another. It is deliberately not built: holding third-party session cookies demands encryption at rest and key management beyond this exercise's scope, and building that badly would be worse than scoping it out.

Practices adopted where their documentation is silent

Their public operation pages document no error format, status codes, pagination, rate limiting, versioning or idempotency. Those gaps are filled from Sean Goedecke's Good API Design, with two of its rules independently corroborating choices Tross already makes — plain API keys, and treating versioning as a last resort.

  • Rate limiting with metadata. X-Limit-Remaining and Retry-After on 429. Not decorative: LinkedIn rate-limits us, so throttling protects the single session the service depends on.
  • Expensive fields optional. input.sections selects which profile sections to fetch, because each additional section costs a separate upstream round trip.
  • Additive evolution only. Unrecognised upstream fields pass through rather than being dropped; documented fields are never removed.
  • Idempotency keys and cursor pagination were considered and rejected. Both are inapplicable to a single-object read, and applying them for appearance would signal checklist-following rather than judgement.

The resulting contract

POST /api/integrations/linkedin/fetch-profile
X-API-Key: <key>

{ "input": { "profileUrl": "https://www.linkedin.com/in/…",
             "sections": ["experience","education","skills"] },
  "auth_id": "b3f1c2e4-8a90-4d21-9f77-2ce1d0a4b512" }
200 OK
{ "profile":  { /* mirrors their "patient" / "claims" / "encounters" */ },
  "warnings": [ { "code": "SECTION_UNAVAILABLE", "section": "certifications",
                  "message": "Not visible to the authenticated session." } ],
  "fetchedAt": "2026-08-27T09:12:33Z" }
4xx / 5xx
{ "error": { "code": "LINKEDIN_SESSION_EXPIRED",
             "message": "The backend LinkedIn session is no longer valid.",
             "retryable": false,
             "requestId": "req_01J8…" } }

The warnings array is the most consequential decision here

LinkedIn returns different amounts of a profile depending on connection degree and the subject's privacy settings. A section that is simply not visible is a normal condition, not a failure. Degrading that section to a warning while returning everything else makes the API honest about partial data instead of collapsing an entire request over one missing field — and the pattern is borrowed directly from Tross's own write responses.

One deliberate deviation

Tross uses POST for reads, against ordinary REST convention. POST is kept as the primary method — it matches their house style, keeps profile URLs out of access logs, browser history and Referer headers, and avoids nesting a URL inside a URL. A documented GET alias is also exposed, because that is what callers reach for first.

08Architecture

09Security posture

  • li_at is HttpOnly. Page JavaScript cannot read it, which is a deliberate defence: a scripting flaw on linkedin.com cannot be escalated into session theft. Obtaining it requires developer tools or a browser extension with cookie permissions. JSESSIONID is deliberately readable, because the page's own scripts must attach it as the CSRF token — two cookies with opposite visibility requirements, both correct.
  • Secrets never enter the repository. The session cookie and API keys are supplied as environment variables; the repository carries a .env.example with empty placeholders and a .gitignore covering the real file.
  • Callers are authenticated and throttled. X-API-Key on every request; 429 with Retry-After beyond the limit.
  • Personal data is kept out of URLs. Profile URLs travel in the request body, so they do not accumulate in access logs or browser history.
  • Outbound calls are throttled and cached, which protects the upstream session as much as it improves latency.

10Legal and ethical posture

Following hiQ Labs v. LinkedIn, accessing public profile data is not a criminal matter under the Computer Fraud and Abuse Act. It nonetheless breaches LinkedIn's Terms of Service as a contractual matter, and LinkedIn enforces that both technically and through litigation.

The relevant precedent

In LinkedIn Corp. v. Nubela Pte. Ltd. / Proxycurl LLC (N.D. Cal., filed January 2025), LinkedIn alleged the creation of hundreds of thousands of fake accounts to scrape millions of profiles, including non-public data, which was then resold through an API. The defendants settled, agreed to permanently delete all data obtained, accepted a permanent injunction, and shut the service down in July 2025.

The conduct that drew the suit was fake-account creation at industrial scale combined with commercial redistribution. This project uses one genuine account, belonging to its author, with no data resale and no automated account creation — a materially different posture, though still a Terms of Service violation and presented as a technical demonstration rather than a production service.

11Known limitations

  • Data visibility is bounded by the authenticated account. Connection degree and the subject's privacy settings determine what LinkedIn returns; missing sections surface as warnings rather than errors.
  • GraphQL queryId hashes rotate. Any fallback path depending on them will break when LinkedIn rotates a persisted query, and the hash must be re-harvested from live traffic.
  • Undocumented endpoints may change without notice. There is no contract, no deprecation window, and no changelog.
  • Single session, single point of failure. If the backing account is restricted, the service degrades to a clear LINKEDIN_SESSION_EXPIRED error rather than partial or wrong data.
  • Every caller receives the operator's view of LinkedIn, not their own. Visibility depends on the backing account's relationship to the subject, so two callers requesting the same profile receive identical data regardless of their own networks. auth_id is a single-session stub; multi-credential support is designed for but not implemented.
  • Not built for volume. No proxy rotation and no account pooling; throughput is deliberately limited to what one session can sustain safely.
  • Section coverage is being verified. The top-card fields are confirmed; the endpoints and decoration IDs serving about, skills, certifications, languages and profile images are still being mapped, and any that prove unreachable will be documented here rather than silently omitted.
